All services are declared in `anyka_rust/supervisor.toml` and started by the
supervisor in file order. Paths in it are relative to `anyka_rust/`. A service with
a `when` condition starts only if the [board profile](/docs/adding-a-board) has that
hardware; on the tested AV100 every service runs.

| Service | Default | Listens on | Purpose |
| --- | --- | --- | --- |
| `wdt_feeder` | on, **critical** | — | Feeds `/dev/watchdog` every second. Started first; the web UI cannot stop it. |
| `lights` | on, `when = "lights"` | `/tmp/kamoder-lights.sock` | Owns the light lines the board profile lists: IR-cut filter, IR and white LEDs, red/blue indicator, speaker amp. Day/night mode, persisted in `etc/lights.json`. |
| `wifi` | on | — | Keeps the station associated, applies `wifi_ssid` changes with rollback, and runs the [recovery ladder](/docs/architecture#wi-fi-recovery). |
| `sshd` | on | TCP **2222** | Password-authenticated SSH (PBKDF2 hashes in `etc/`). |
| `web` | on | TCP **80**, **443** (HTTPS, self-signed) | Admin SPA and JSON API: login, services, Wi-Fi, PTZ, lights, audio, updates, users, reboot. |
| `onvif` | on | TCP **8000**, UDP **3702** | ONVIF Profile S: device, media, PTZ and imaging (IR-cut), plus WS-Discovery. Owns the PTZ motor. |
| `rtsp` | on, `when = "video.encoder"` | TCP **554**, `/vs0`, `/vs1`, … | RTSP 1.0, H.264 over TCP-interleaved or UDP, Digest auth with the ONVIF account. One `vsN` path per sensor in the board profile. |
| `snapshot` | on, `when = "video"` | `127.0.0.1:3000`, `/tmp/kamoder-video.sock` | The camera service (`bin/camera serve`): captures every sensor with the board's video backend, hardware H.264 for `rtsp`, JPEG snapshots and `/status` for `web` and `onvif`. No vendor library. |
| `audio` | on, `when = "audio"` | `/tmp/kamoder-audio.sock` | Owns the codec: microphone frames for RTSP and web Listen, speaker playback for push-to-talk and ONVIF talk-back. Gains in `etc/audio.json`. See [Audio](/docs/audio). |
| `update` | on | `/tmp/kamoder-update.sock` | Checks GitHub for signed updates, installs to the inactive A/B slot and commits a trial boot once healthy. See [Updates](/docs/updates). |

## Supervisor

- Restarts a service that exits, with exponential backoff.
- Stops restarting after too many crashes in a window (per service
  `max_restarts` / `restart_window_secs`).
- Exposes a control socket the web UI uses to list, start, stop and restart services.
  Critical services refuse to be stopped.

To change what runs, edit `supervisor.toml` on the card (`enabled = false`, `args`)
and restart the stack with `sh anyka_rust/init.sh --stop` followed by
`sh Factory/config.sh`.

## Logs

Every service logs through `tracing` to `anyka_rust/logs/<service>.log`. The level is
`log_level` in `camera.conf` (for example `info,wifi=debug`). Boot is logged to
`logs/boot.log` and `logs/init.log`, and every call of the boot hook to
`/tmp/anyka_config_sh.log`.

## Metrics

Set `metrics='textfile:/mnt/disc1/anyka_rust/metrics'` and each service writes
`<service>.prom` for node_exporter's textfile collector. All metric names start with
`kamoder_`, for example `kamoder_wifi_escalation_level` or
`kamoder_lights_*`.

## Demos

The vendor SDK's demo programs are ported for experiments: `ai_demo`, `aenc_demo`,
`venc_demo`, `md_demo`, `md_demo_v8`, `rtsp_demo` and `jpeg_snapshot`. They are not
part of a normal build; `./x dist --with-demos` (or `./x sd --with-demos`) adds them
to `bin/` together with the SDK objects they load. Run one with
`sh anyka_rust/run-on-camera.sh <demo> [args]`. All but `md_demo_v8` use the EV200
SDK, which does not match the AV100's video pipeline; `md_demo_v8` uses the AV100's
V8 SDK and is not yet tested on hardware. None of them is needed for video: the
camera service drives the AV100 without the SDK.
