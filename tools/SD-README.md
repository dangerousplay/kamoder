# anyka_rust — Rust camera stack on the SD card

Generated by `./x sd` in `rust-cross-compile/`. Do not edit `bin/`, `lib/` or
the scripts here — edit the sources in `rust-cross-compile/tools/` and rerun
`./x sd`. The files listed under **Camera-owned** are never touched by it.

## Install

1. Copy `camera.conf.example` to `camera.conf` (`./x sd` does this once) and
   fill in:
   * `ssh_password` — hashed into `etc/anyka-sshd.passwd` on first boot, then
     blanked from `camera.conf`.
   * `wifi_ssid` / `wifi_password` — **only** if you want the card to move the
     camera to a network. Leave `wifi_ssid` empty to keep the manual
     configuration; see **Wi-Fi** below.
2. Copy `autorun.sh`, `Factory/` and `anyka_rust/` to the root of the card.
3. Boot, then start the stack by hand (see below). Chain:
   `Factory/config.sh` → `init.sh` → `supervisor` → `wdt_feeder`,
   `wifi`, `sshd`, `web`, `onvif`.

**The AK3918AV100 stock firmware runs nothing from the SD card at boot**
(verified 2026-09-27; see `docs/notes/HARDWARE-FINDINGS.md` §9). The
`Factory/config.sh` hook only exists on the AK3918EV200. On the AV100, after
every boot, run from telnet, UART or ssh:

```sh
sh /mnt/disc1/Factory/config.sh
```

## Layout

| Path | What |
|---|---|
| `bin/` | stripped binaries (full-debug copies are in `rust-cross-compile/dist/`) |
| `lib/{audio,video,md,rtsp}/` | EV200 SDK variants — each binary's RPATH picks one |
| `lib/v8/` | AK3918AV100 V8 SDK, used by `md_demo_v8` |
| `lib/sys/` | runtime every binary loads from the card: empty `libpthread`/`libm`/`librt`/`libdl` stubs (the camera's libc already has them) and the firmware's `libgcc_s.so.1`, `libstdc++.so.6`. Only `libc.so.0` and `ld-uClibc` come from the firmware, so binaries in `bin/` run directly, no `LD_LIBRARY_PATH` |
| `init.sh` | starts and restarts the supervisor; `--check`, `--fg`, `--stop` |
| `run-on-camera.sh` | run any binary by hand: `sh run-on-camera.sh md_demo_v8 50` |
| `supervisor.toml` | services, restart policy, log rotation |
| `camera.conf.example` | every setting, documented |

**Camera-owned** (created on the camera, preserved by `./x sd`, gitignored):
`camera.conf`, `etc/` (sshd credentials and host key), `logs/`, `backup/`
(Wi-Fi config backups; `wpa_supplicant0.conf.orig` is the camera's own and is
never overwritten), `metrics/`.

## Services

| Service | Default | Notes |
|---|---|---|
| `wdt_feeder` | on | first, so the hardware watchdog is fed before anything slow starts |
| `wifi` | on | `wifi`: Wi-Fi reconciler, see below |
| `sshd` | on | port 2222, password login, runs as root |
| `rtsp` | off | Rust RTSP server (`rtsp://<camera>:554/vs0`, Digest with the ONVIF account); waits for the Phase C encoder source, plays an Annex-B file meanwhile |
| `snapshot` | off | EV200 SDK; the ISP does not produce frames on this camera |

## Wi-Fi

`wifi` checks the link every 10 s: wpa_supplicant `STATUS` over its
control socket, the address on `wlan0`, and whether the default gateway
answers ARP. Healthy means all three, on the configured SSID.

* **Healthy** → the config is recorded as last-known-good in
  `backup/wpa_supplicant0.conf.good` (before anything moves the camera off it).
* **`wifi_ssid` set and different from `/rom/wpa_supplicant0.conf`** → backs
  up the current config (`backup/…orig` once, `…last` each time; best-effort),
  writes the new one atomically, reassociates. This also undoes a network
  something else configured — but a network that was *just* switched to first
  gets the grace period, so if it works it is recorded as a way back before
  being replaced.
* **Gateway silent on an otherwise up link** → tolerated until it misses 3
  checks in a row (`--gateway-failures`). Losing the association or the
  address counts at once.
* **Unhealthy** → 45 s grace (none for a silent gateway, the 3 checks were
  the wait), then a recovery ladder with backoff (10 s doubling, never more
  than 5 min, repeated for as long as the link is down):
  1. `renew` (once, only while still associated): wpa_supplicant
     `REASSOCIATE` over its socket plus a DHCP renew (udhcpc SIGUSR1);
  2. `reassociate`: the full station restart (wpa_supplicant + udhcpc);
  3. after 2 failed restarts on a network known to work, `reset_driver`:
     `rmmod ssv6x5x`, `insmod /ipc/modules/wifi/ssv6x5x.ko stacfgpath=…`
     (`--driver-*` options), `wlan0` up, station restart;
  4. after that fails too, `power_cycle`: the USB Wi-Fi module's power
     (GPIO 98) off for 3 s and back on to the level in
     `/rom/usb_module_power_on`, then the driver reset. GPIO 98 is only
     touched if `setup.sh` exported it as an output, and always switched
     back on, even when a later step fails. At start-up `wifi` restores it if
     it finds it off.

  `rmmod`/`insmod` have timeouts, so a wedged driver cannot hang the loop.
  Where a hardware step does not apply (no `ssv6x5x` loaded, GPIO 98 not
  set up), it logs that and restarts the station instead.
  `--driver-reset-after 0` turns both hardware steps off and
  `--power-cycle-after 0` turns off the power cycle. Metrics:
  `kamoder_wifi_escalation_level`, `kamoder_wifi_gateway_failures`,
  `kamoder_wifi_actions_total{action=…}`.
* **Still down after 4 retries** → **roll back** to the last-known-good network,
  and hold *that* failed network off for 30 min. Changing `camera.conf` to
  anything else (fixing a typo) takes effect immediately. A network that was
  never seen working is not given the hardware steps: it gets plain restarts
  and then the rollback.
* Only Wi-Fi daemons in the camera's own network namespace are ever stopped.

```sh
cd /mnt/disc1/anyka_rust
sh run-on-camera.sh wifi status          # what it sees and would do
sh run-on-camera.sh wifi --dry-run       # log decisions, touch nothing
sh run-on-camera.sh wifi --help
```

Validated on a simulated camera (`./x itest`: the firmware's own
wpa_supplicant/hostapd over `mac80211_hwsim`), not yet on the camera. For the
first deployment, consider running
it with `--dry-run` (add it to `args` in `supervisor.toml`) and reading
`logs/wifi.log` before letting it act.

## Hard rules

* **Never start `/ipc/ipc`.** It rewrites the Wi-Fi configuration. Nothing on
  this card starts it; once started, `init.sh` stops it (`stop_vendor_ipc=1`,
  the default) like the old quite_console.sh — including `main`/`anyka_ipc`,
  and again whenever they reappear — and `wdt_feeder -w` takes over the
  watchdog as soon as the vendor app releases it.
* `telnetd` (port 23) is an unauthenticated root shell and `sshd` has no
  privilege separation. Trusted network only. Set `start_telnetd=0` once SSH is
  proven.
* `/mnt` is a 16 MB tmpfs on this camera; the card is `/mnt/disc1`.

## Logs

All on the card under `logs/`, rotated at 1 MiB, 5 generations:
`init.log`, `wifi.log`, `boot.log`, `supervisor.log`, and one per service.
